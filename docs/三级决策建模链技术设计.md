### 设计第 2 节：三级决策建模链

```text
业务输入 / 仓库上下文 / 外部状态快照
                ↓
     ① 本地规则层：确定、可导入、可审计
                ↓                                          ↓ 
 ② 行业/场景模板层：把输入编译为 Choice 请求    ③ LLM 建模层：受限生成问题、候选项与路由建议草案
                ↓
     Choice host 路由：规则优先，按成本 / 延迟 / 健康度选择 host
                ↓
     原始 Jev Choice response + 独立 DecisionReceipt + ActionIntent
```

#### ① 本地规则层

规则以 JSON/YAML 导入，采用受限声明式表达式，不能执行任意 JavaScript。作用域从低到高为模板默认、组织策略、环境策略和本次调用策略。

它只允许四类动作：

- `reject`：输入、状态、问题或候选项不合格时拒绝调用。
- `constrain`：限制候选项数、必须包含 `other`/`needs-review`、禁止某类候选行动。
- `route`：规定优先 host、预算、最大延迟、重试、熔断与降级顺序。
- `shortCircuit`：确定性规则已足够时直接产出兼容 Choice 的结果，例如概率为 `1.0` 的唯一选项。

`shortCircuit` 的返回仍是标准 Choice envelope，只是 `model` 标记为 `yueli-dex/rules@1`；不会伪装成远程 Jev 的回答。真实 provider、触发规则和原因只进入 `DecisionReceipt`。

#### ② 行业/场景模板层

模板是版本化、可安装的配置包，默认纯 YAML/JSON、无代码执行能力：

```yaml
apiVersion: yueli-dex-template/v1
id: support-triage
version: 1.0.0

inputSchema: ./ticket.schema.json
state:
  from:
    message: $.message
    accountPlan: $.account.plan

choice:
  id: handler
  instructions: Which team should own this request?
  criteria:
    billing: Payments, invoices, refunds, and subscriptions
    technical: Product bugs, incidents, and integrations
    needs-review: Evidence is insufficient or spans multiple teams

constraints:
  requireFallbackOption: needs-review
  maxOptions: 12

actions:
  billing: { kind: queue.assign, queue: billing }
  technical: { kind: queue.assign, queue: technical }
  needs-review: { kind: review.request }
```

模板的 `actions` 仅定义可审计的行动意图；DEX 不执行队列写入、工具调用或代码。下游系统可以消费 `ActionIntent`，并自行授权和执行。

#### ③ LLM 动态建模层

LLM 不是 Choice 的替代 provider，而是模板编译前的受控“建模助手”。它可提交 `ModelingProposal`，其中包括动态问题、候选项、候选项说明、所需仓库证据和 host 路由建议。

提案必须依次经过：

1. JSON Schema、最大 255 个候选项及稳定 ID 校验；
2. 模板约束校验：候选项是否互斥、是否保留兜底项、是否越出行业边界；
3. 本地规则审查：敏感字段、允许的行动意图、host 白名单与预算；
4. 保存版本、输入证据摘要与差异，再编译为原生 Choice 请求。

代码仓库只作为受控上下文源：由 `ContextProvider` 插件在允许路径、脱敏规则与 token 预算内读取快照；LLM 或模板都不能借此执行仓库代码。

我建议保留本地规则的 `shortCircuit` 能力：它满足“第一层 Rule Engine”，且响应仍完全是 Choice 格式。请确认这一点，以及模板只产出 `ActionIntent`、不直接执行行动的边界；确认后我继续定义 Provider/模板/建模插件 manifest、路由算法和测试验收标准。

本地规则层始终包裹建模与路由；场景模板和 LLM 建模器是两条并列的请求构建路径。已有合适模板时，直接编译并调用 Choice，不调用 LLM。只有模板不存在、模板显式允许扩展，或调用方明确选择动态建模时，才启用 LLM 建模器。Annotation 1

```text
业务输入 / 仓库上下文 / 外部状态快照
                ↓
        本地规则层：约束、校验、路由
                ↓
      ┌─────────┴──────────┐
      ↓                    ↓
场景模板编译           LLM 动态建模
已有模板直接使用       仅按需、受模板/规则约束
      └─────────┬──────────┘
                ↓
       原生 Jev Choice request
                ↓
  Host 路由、重试、熔断与降级
                ↓
原始 Choice response + Receipt + ActionIntent
```

### 设计第 3 节：开放插件与多 Host 路由

所有插件都使用同一 manifest，声明兼容版本、配置 schema、能力和入口；安装时校验，运行时不会按字符串动态加载未知模块。

```json
{
  "apiVersion": "yueli-dex-plugin/v1",
  "id": "@haxitag/yueli-dex-provider-typesafe",
  "kind": "provider",
  "version": "0.1.0",
  "requires": { "yueliDex": "^0.1.0" },
  "capabilities": ["choice"],
  "configSchema": "./config.schema.json",
  "entry": "./dist/index.js"
}
```

插件分四类：

- `provider`：接收标准 Choice request，返回标准 Choice response；包含 TypeSafe、Cloudflare、Vercel 与自部署 HTTP provider。
- `template-pack`：纯数据模板包；默认不允许执行代码。
- `modeler`：按需生成 `ModelingProposal`，不能直接调用 Choice host 或执行行动。
- `context-provider`：在路径白名单、脱敏和 token 预算内提取仓库或业务上下文快照。

自部署 Provider 的默认兼容模式是 `jev-choice/v1`，即接受 TypeSafe 的 `state / model / questions` 请求形状，并返回 `model / answers / usage`。不兼容的服务必须自行提供 Provider 插件，不能通过宽松解析污染核心契约。

路由由核心的声明式策略负责，不交给单个 Provider：

```yaml
providers:
  - id: typesafe-primary
    plugin: "@haxitag/yueli-dex-provider-typesafe"
  - id: cf-edge
    plugin: "@haxitag/yueli-dex-provider-cloudflare"
  - id: private-jev
    plugin: "@acme/private-jev-provider"

routes:
  - when:
      template: support-triage
    prefer: [cf-edge, typesafe-primary, private-jev]
    limits:
      maxEstimatedCostUsd: 0.002
      p95LatencyMs: 900
      maxAttempts: 2
```

选择顺序为：本地规则筛选可用 host → 排除熔断或预算不满足者 → 按静态优先级、实时延迟、近期成功率和成本估算排序。仅网络超时、限流或可重试服务端错误可触发同请求的 failover；收到合法 Choice 响应后，即使低置信度也不切换 host，因为低置信度是决策信号而非服务故障。

每次尝试都记录到 `DecisionReceipt`：请求哈希、模板/规则版本、候选 host、实际 host、耗时、重试、估算成本和失败分类。密钥只以环境变量或宿主 secret binding 引用，绝不写入模板、规则或 receipt。

请确认这套插件类型与路由边界；确认后我给出 SDK 精确签名、模板 DSL、测试矩阵与分阶段集成计划，并写入正式设计规格。

### 设计第 4 节：SDK、模板 DSL 与验收门

SDK 保留原生 Jev 请求/响应；DEX 配置与审计放在客户端实例，不进入请求 body。

```ts
type JsonValue =
  | string | number | boolean | null
  | JsonValue[] | { [key: string]: JsonValue };

interface ChoiceQuestion {
  type: "choice";
  instructions: JsonValue;
  criteria: Record<string, JsonValue>;
}

interface ChoiceRequest {
  state: JsonValue;
  model?: string;
  questions: Record<string, ChoiceQuestion>;
}

interface ChoiceAnswer {
  type: "choice";
  choice: string;
  confidence: number;
  probabilities: Record<string, number>;
}

interface ChoiceResponse {
  model: string;
  answers: Record<string, ChoiceAnswer>;
  usage?: { input_tokens: number; output_tokens: number };
}

const dex = createDex({
  providers,
  routing,
  ruleSets,
  receiptStore,
});

const response: ChoiceResponse = await dex.choice(request);
```

模板侧只负责编译或准备请求：

```ts
const request = await dex.templates.prepare({
  template: "support-triage@1.0.0",
  input: ticket,
});

const response = await dex.choice(request);

const intent = dex.templates.toActionIntent({
  template: "support-triage@1.0.0",
  request,
  response,
});
```

`toActionIntent()` 是纯函数，绝不触发外部操作。动态建模则明确分两步，防止 LLM 草案绕过规则：

```ts
const proposal = await dex.modeling.propose({
  template: "support-triage@1.0.0",
  input: ticket,
  context: repoSnapshot,
});

const request = await dex.modeling.accept(proposal);
// 校验、规则与审计通过后，才得到 ChoiceRequest
```

模板 DSL 增加动态扩展位，但默认关闭：

```yaml
apiVersion: yueli-dex-template/v1
id: code-change-review
version: 1.0.0

inputSchema: ./change.schema.json
context:
  - provider: repository
    paths: ["src/**", "package.json"]
    redact: ["**/.env*", "**/*secret*"]
    maxTokens: 12000

choices:
  - id: next_action
    state: ./state-map.yaml
    instructions: Select the safest next action.
    criteria:
      review: Request human review before proceeding
      test: Run the specified verification suite
      revise: Return the change for revision
      needs-context: Evidence is insufficient
    actions:
      review: { kind: review.request }
      test: { kind: verification.request }
      revise: { kind: revision.request }
      needs-context: { kind: context.request }

modeling:
  mode: optional
  allow:
    refineInstructions: true
    addCriteria: false
    changeActionKinds: false
  requireEvidenceRefs: true
```

动态建模只能在模板准许的字段内提出差异；如需新增候选项，模板必须显式开放 slot、定义数量上限和可映射的行动意图。否则 LLM 只能建议，不能编译为请求。

验收按五组测试建立：

1. 契约测试：严格验证请求和响应；每个 `choice` 必须在 `criteria` 内，概率非负且总和约为 1。
2. Provider 测试：TypeSafe、Cloudflare、Vercel、标准自部署 HTTP 的请求映射、认证错误与响应归一化夹具。
3. 路由测试：成本/延迟/健康度排序、超时与 429 failover、熔断、预算拒绝；合法低置信度响应不得重试。
4. 模板/建模测试：静态模板编译、动态草案的越权字段、重复或重叠候选项、缺失兜底项、仓库路径越界与敏感数据脱敏。
5. 端到端测试：本地标准兼容 server 的确定性链路；凭据存在时才运行真实 TypeSafe、Cloudflare、Vercel smoke，并记录观察结果，不把一次成功宣称为稳定性证明。

完成标准是：所有包可构建、对外类型稳定、四类 Provider 契约通过、三级链路可由本地测试完整复现、模板安装与动态建模提案都有审计记录，且真实 host smoke 独立报告。

请确认这份最终接口与验收设计。确认后我会将完整规格写入仓库、进行一致性自查，请你审阅规格文件后再进入实现计划与实际开发。
