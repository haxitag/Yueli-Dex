# Yueli DEX 调用说明与使用手册

## 1. 阅读前说明

Yueli DEX 的定位是为 Jev `Choice` 提供统一接入、决策建模和稳定路由。它不是新的模型原语，也不会把 Choice 改成文本生成、评分或布尔判断。

本文描述已确认的 v1 接口与行为契约。当前项目处于文档和设计完成、实现尚未开始的阶段：下文的“计划 SDK”示例不可直接安装运行；TypeSafe、Cloudflare 和 Vercel 的官方 API 请以各自官方文档为准。

## 2. 最小心智模型

一次 Choice 决策始终由以下四项组成：

```yaml
state: 要判断的事实、上下文或结构化状态
question: 要作出的一个边界明确的判断
criteria: 可供选择且能够相互区分的候选项
choice: 模型选择的候选项，以及完整概率分布和置信度
```

DEX 的价值不在改变最后一次 Choice 调用，而在调用前帮助接入者构造可用的 `state + question + criteria`，并在多个同构 host 之间可靠地发送同一个请求。

## 3. 原生 Choice 请求和响应

### 3.1 请求

```json
{
  "state": "My payment was charged twice and I need a refund.",
  "model": "jev-latest",
  "questions": {
    "handler": {
      "type": "choice",
      "instructions": "Which team should handle this request?",
      "criteria": {
        "billing": "Payments, invoices, refunds, and subscriptions",
        "technical": "Product bugs, incidents, and integrations",
        "needs_review": "Evidence is insufficient or does not fit another option"
      }
    }
  }
}
```

字段规则：

- `state` 可以是字符串、数组或 JSON 对象。它应只包含与本次问题相关、经授权可发送的事实。
- `model` 是可选字段。它由被选中的 host 解释；路由规则可以限制允许的模型。
- `questions` 可包含多个问题，但每个问题必须都是 `type: "choice"`。
- `instructions` 只问一个明确、可由所给状态判断的问题；不要把“定位原因、确定负责人、执行修复”混为一个问题。
- `criteria` 的 key 是稳定的机器标识，value 是给模型的区分说明。相近选项必须明确边界。
- 每个问题最多 255 个候选项。对于开放世界分类，应增加 `needs_review`、`other` 或同类兜底项；深层分类应分层提出多个 Choice 问题。

### 3.2 响应

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "handler": {
      "type": "choice",
      "choice": "billing",
      "confidence": 0.81,
      "probabilities": {
        "billing": 0.87,
        "technical": 0.08,
        "needs_review": 0.05
      }
    }
  },
  "usage": {
    "input_tokens": 250,
    "output_tokens": 28
  }
}
```

DEX 验证以下条件后才把 provider 响应交给调用方：答案类型是 `choice`；被选的 key 存在于原请求的 `criteria`；概率 key 集合与候选项集合相同；每个概率和 `confidence` 都在 `0` 到 `1`；概率总和在数值容差内等于 `1`。

有效的低置信度结果不是错误。它表示证据不足或候选项相近，调用方应根据自己的业务策略请求更多上下文、交给人工复核或走声明的兜底意图，而不应重试另一个 host 企图获得更高置信度。

## 4. 计划 SDK 调用方式

### 4.1 直接调用 Choice

```ts
// 计划 SDK，尚未发布
import { createDex } from "@haxitag/yueli-dex";

const dex = createDex({
  providers: [/* TypeSafe / Cloudflare / Vercel / self-hosted adapters */],
  routing: { /* 默认及命名路由策略 */ }
});

const response = await dex.choice({
  state: { message: "I was charged twice.", plan: "pro" },
  questions: {
    handler: {
      type: "choice",
      instructions: "Which team should own this request?",
      criteria: {
        billing: "Payments, charges, refunds, invoices, and subscriptions",
        technical: "Product bugs, outages, and integrations",
        needs_review: "The evidence is insufficient or overlaps categories"
      }
    }
  }
});
```

`dex.choice()` 返回原生 Choice response；不会附加 `provider`、`route`、`action` 或其他 DEX 私有字段。

### 4.2 获取审计信息

```ts
// 计划 SDK，尚未发布
const unsubscribe = dex.on("choice.completed", ({ request, response, receipt }) => {
  console.log(receipt.decisionId);
  console.log(receipt.route.selectedProviderId);
  console.log(receipt.timing.elapsedMs);
});

// 在不再需要监听时调用
unsubscribe();
```

`DecisionReceipt` 是并发安全的 sidecar，包含请求哈希、模板和规则版本、候选/实际 host、重试、耗时与安全的失败分类。它不保存 API key、完整敏感状态或未脱敏仓库内容。

## 5. Host 配置和路由

### 5.1 支持的 host

| Host | 计划适配器 | 接入方式 |
| --- | --- | --- |
| TypeSafe | `@haxitag/yueli-dex-provider-typesafe` | 官方 `POST /v1/systemone` |
| Cloudflare | `@haxitag/yueli-dex-provider-cloudflare` | Workers AI binding 或 Account REST 的 `typesafe/jev` |
| Vercel | `@haxitag/yueli-dex-provider-vercel` | AI Gateway 的 evaluation 集成 |
| Self-hosted | `@haxitag/yueli-dex-provider-http` | 声明 `jev-choice/v1` 的标准 HTTP 服务 |

自部署服务必须接受标准 Choice body 并返回标准 Choice body。字段名不同、仅返回一个 label、概率不完整或不归一的服务不属于 `jev-choice/v1`；应实现专用 Provider 插件，而不是依赖 DEX 猜测或静默转换。

### 5.2 路由策略

```yaml
# 计划配置，尚未由 CLI 读取
providers:
  - id: cf-edge
    plugin: "@haxitag/yueli-dex-provider-cloudflare"
  - id: typesafe-primary
    plugin: "@haxitag/yueli-dex-provider-typesafe"
  - id: private-jev
    plugin: "@acme/private-jev-provider"

routes:
  default:
    prefer: [cf-edge, typesafe-primary, private-jev]
    limits:
      maxEstimatedCostUsd: 0.002
      p95LatencyMs: 900
      maxAttempts: 2
```

路由步骤是：本地规则筛选 host → 排除未配置凭据、无 Choice 能力、熔断或超预算的 host → 用明确优先级叠加近期延迟、错误率和成本估算排序 → 调用一个 host。

只有连接故障、超时、配置为可重试的服务端错误或限流才可 failover。认证、请求 schema、响应 schema 等问题默认直接失败，以暴露配置错误。一个 host 返回合法 Choice 后不再切换，即使该答案置信度很低。

## 6. 本地规则引擎

规则是 YAML/JSON 的受限声明，不执行 JavaScript、正则、远程请求或时间相关表达式。支持的条件操作符为 `exists`、`equals`、`in`、`lt`、`lte`、`gt`、`gte`。

```yaml
apiVersion: yueli-dex-rules/v1
rules:
  - id: regulated-workloads-use-approved-route
    when:
      all:
        - path: $.input.tenantTier
          op: equals
          value: regulated
    then:
      kind: route
      route: regulated-primary

  - id: require-review-fallback
    when:
      all:
        - path: $.compiled.questions.handler.criteria.needs_review
          op: exists
    then:
      kind: constrain
      requireFallbackOption: needs_review
```

规则动作只有四种：

- `reject`：在发生网络调用前阻止无效或不允许的请求。
- `constrain`：强制候选项数量、兜底项、状态要求或行动意图白名单。
- `route`：指定已审批的路由策略。
- `shortCircuit`：规则充分确定时返回 `model: "yueli-dex/rules@1"` 的标准 Choice response。它会诚实标记本地规则来源，并为所有候选项生成完整概率分布。

## 7. 使用场景模板

模板把行业知识、业务输入和约束编译为 Choice request。存在匹配模板时不需要 LLM。

```yaml
apiVersion: yueli-dex-template/v1
id: support-triage
version: 1.0.0

inputSchema: ./ticket.schema.json
state:
  from:
    message: $.message
    accountPlan: $.account.plan

choices:
  - id: handler
    instructions: Which team should own this request?
    criteria:
      billing: Payments, invoices, refunds, and subscriptions
      technical: Product bugs, incidents, and integrations
      needs_review: Evidence is insufficient or spans multiple teams

actions:
  handler:
    billing: { kind: queue.assign, queue: billing }
    technical: { kind: queue.assign, queue: technical }
    needs_review: { kind: review.request }
```

调用时，计划 SDK 的 `dex.templates.prepare()` 返回原生 `ChoiceRequest`；`dex.templates.toActionIntent()` 将结果映射成零个或多个 `ActionIntent`。后者是纯数据，例如 `queue.assign` 或 `review.request`，不代表 DEX 已经调用队列或执行了操作。

模板包默认是可审查的纯数据。需要自定义可执行编译器的模板必须作为受信任的插件安装，不应把从网络下载的 YAML 当作可执行代码。

## 8. 何时使用 LLM 动态建模

LLM 动态建模与场景模板并列，不是模板的固定下一步。适合以下情形：

- 找不到满足任务的模板；
- 模板明确开放了问题措辞或候选项扩展位；
- 需要从批准的仓库快照或业务上下文中提出候选项草案。

模型器只能产出 `ModelingProposal`。它包含候选 Choice request、证据引用和路由建议；随后仍要经过 schema、模板权限、本地规则、路径白名单、脱敏和 token 预算校验。接受后的产物才是可调用的 Choice request。

没有模板的动态请求可以在组织级规则允许时执行，但没有 `ActionIntent` 映射。若需要安全地关联下游行动，应先发布或选择模板。

## 9. 插件作者说明

插件 manifest 使用 `yueli-dex-plugin/v1`，并声明 `provider`、`template-pack`、`modeler` 或 `context-provider` 之一。Provider 的唯一职责是把不变的 `ChoiceRequest` 发送给 host，并返回已验证的 `ChoiceResponse`。

```json
{
  "apiVersion": "yueli-dex-plugin/v1",
  "id": "@acme/private-jev-provider",
  "kind": "provider",
  "version": "1.0.0",
  "requires": { "yueliDex": "^0.1.0" },
  "capabilities": ["choice"],
  "configSchema": "./config.schema.json",
  "entry": "./dist/index.js"
}
```

Provider 不得修改问题、候选项或有效答案，不得自动创建 ActionIntent，也不得把凭据写进日志或 receipt。可执行插件是受信任的应用代码；安装前应审查来源、版本与依赖。

## 10. 故障处理与安全清单

常见、可机器处理的错误码：`RULE_REJECTED`、`TEMPLATE_INVALID`、`MODELING_PROPOSAL_REJECTED`、`NO_ELIGIBLE_PROVIDER`、`PROVIDER_AUTH`、`PROVIDER_TIMEOUT`、`PROVIDER_RATE_LIMIT`、`PROVIDER_FAILURE`、`INVALID_CHOICE_RESPONSE`。

上线前至少检查：

1. 候选项描述互斥，且保留适当兜底项。
2. `state` 不含不应发往所选 host 的密钥、个人数据或未脱敏源码。
3. 路由策略、预算、超时和 fallback 已在目标环境配置。
4. 模板/规则/插件版本进入 receipt，方便复现一次决定。
5. 下游执行器把 `ActionIntent` 当作请求而不是授权；高风险操作仍需其自身权限与审批。
6. 真实 host smoke 与本地测试分开记录；一次成功调用不等于 SLA、成本或长期稳定性证明。
